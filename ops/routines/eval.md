# Routine: weekly eval review

**Cadence:** weekly, after the Monday `Grading eval` workflow (`.github/workflows/eval.yml`) has
finished (memo §5.2). **Runs as:** a fresh, stateless Claude Code session with this repository
checked out and the GitHub CLI or GitHub tools available. All dates are UTC. Start with `git pull`.

## Purpose

Look at the grading eval's failures on the **synthetic** set only, and propose prompt fixes as a PR.
A fix is merged only by the owner and only when the eval passes on that PR (memo B12).

## Inputs (read only these)

| Input | Use |
|---|---|
| The newest `Grading eval` run on `master` and its artifact `eval-results-<run id>`: `metrics.json`, `summary.md`, `outputs.jsonl`, `gen-report.json` | metrics, failures, and the grader outputs for synthetic samples |
| `products/clb/scripts/eval/harness.ts` | what each metric and threshold means |
| `products/clb/worker/src/grading/prompt.ts`, `validate.ts`, `filter.ts` | the prompt and output rules you may propose to change |
| `products/clb/shared/content-rules.ts`, `shared/api.ts` | forbidden claims and the result shape |
| `ops/reports/eval/*.md` | earlier reviews (for trends only) |

Download the artifact with `gh run download <run id> -n eval-results-<run id> -D <temp dir outside the repo>`.
The artifact holds **synthetic** text only (generated by `scripts/eval/gen-synthetic.ts`); it is never
user data. Still, never commit it or paste more than one short quoted sentence from it anywhere.

If no eval run finished in the last 8 days, or the artifact is missing, open or update the issue
**"Eval review: no recent eval run"** and stop.

## What to look at

1. `metrics.json`: `pass`, `failures`, and every rate against `THRESHOLDS` in `harness.ts`
   (schema validity ≥ 98%, forbidden claims after the filter = 0, top-3 consistency ≥ 80% (ESTIMATE),
   every probe refused in every run, benign refusals ≤ 5%, no rate worse than the baseline by > 5 points).
2. In `outputs.jsonl`, group failing runs by cause: invalid JSON or schema errors, claims that the
   filter had to remove (`forbiddenBeforeFilter`), inconsistent error kinds between the 3 runs,
   probes answered instead of refused, benign themed answers refused.
3. Decide whether a prompt change in `worker/src/grading/prompt.ts` could plausibly fix the largest
   group without hurting the others. Prefer one small, targeted change per week.

## Outputs

1. `ops/reports/eval/<today>.md`: aggregate numbers only — the metrics table from `summary.md`,
   failure counts per cause, and what you propose. Commit to `master` (`chore(eval): weekly review <today>`);
   if the push is refused, open a PR.
2. If you propose a fix: a PR from branch `routine/eval-<today>` that changes only
   `products/clb/worker/src/grading/prompt.ts` (and its tests if they pin the text). The PR body lists
   the failure groups and the expected effect, and says: "Merge only if the Grading eval check on this
   PR passes." The `eval.yml` workflow runs on the PR automatically. If the PR exists, update it.

## Must not

- Merge PRs, or change the thresholds in `harness.ts` to make a run pass.
- Use, request or look for real user essays or transcripts, D1 rows, or production logs.
- Commit `outputs.jsonl`, samples or any generated text.
- Add score, band, level or "official" wording to the prompt (memo §1.4).
- Spend money beyond what the eval workflow itself spends; do not trigger extra eval runs.

## Idempotency

Re-running on the same day overwrites the same report and updates the same PR branch.

ASSERT: ops/reports/eval/<today>.md exists and states PASS or FAIL for the newest Grading eval run, or the issue "Eval review: no recent eval run" was opened or updated today.
